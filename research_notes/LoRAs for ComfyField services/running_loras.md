## Comfy Cloud: can a workflow use LoRAs that are not preinstalled, how are they imported, what limits apply, which LoRAs are preinstalled, and how does Comfy API v2 / the Comfy SDK refer to model files?

### Takeaway
A shipped ComfyField format can only rely on the 652 LoRAs Comfy Cloud preinstalls, referenced by exact filename in a core `LoraLoader`/`LoraLoaderModelOnly` node. Any other LoRA must either be imported per user (Creator plan or higher, from a Hugging Face or Civitai URL, private to that user) or the run goes to a Pod. Cloud preinstalls exactly the Qwen-Image-Edit 2511 LoRAs ComfyField's planned relight and multiple-angles formats need, so those can run on Cloud with no import.

### Cited Findings

**Import (bring your own LoRA)**
- Comfy Cloud imports models "directly from Civitai and Hugging Face"; the Requirements section says Creator subscription or higher, while the FAQ on the same page says "Creator and Pro plans only" (internal inconsistency) — [Comfy docs: Import models](https://docs.comfy.org/cloud/import-models)
- UI flow: Model Library (left sidebar) → Import → paste a Civitai download-button link or a Hugging Face "Copy Download Link" → pick model type and target folder → wait for download → model shows under "My Models" — [Comfy docs: Import models](https://docs.comfy.org/cloud/import-models)
- Only `.safetensors` (or `.sft`) files; chunked files must be merged first; FAQ says "effectively no file size limit (up to 100GB)"; no count or storage cap is stated; the `nlf` folder is blocked; any folder in the import type selector (e.g. `loras`, `checkpoints`, `diffusion_models`, `vae`) is allowed — [Comfy docs: Import models](https://docs.comfy.org/cloud/import-models)
- Imported models are private to the importing user, can be deleted by that user, and no sharing option is described; local-file upload is not supported (host on a public HF or Civitai repo first) — [Comfy docs: Import models](https://docs.comfy.org/cloud/import-models)
- Private models: save a Civitai API key or a Hugging Face read token under Cloud Settings → Secrets and import the same way — [Comfy docs: Import models](https://docs.comfy.org/cloud/import-models). Conflict: the same page's FAQ still says to upload to a *public* repo first, and the anonymous Cloud feature flags report `private_models_enabled: false`, `model_upload_button_enabled: true`, `max_upload_size: 104857600` (100 MiB) — [cloud.comfy.org/api/features](https://cloud.comfy.org/api/features)
- The import page does not mention any API or SDK use for imported models, nor how a workflow references them — [Comfy docs: Import models](https://docs.comfy.org/cloud/import-models)

**API endpoints that touch model files (Cloud v1 OpenAPI)**
- `POST /api/assets/download` "Initiates a background download job for large files from Huggingface or Civitai"; body `source_url` ("must be from huggingface.co or civitai.com"), optional `tags` (example `["model", "checkpoint"]`), `user_metadata`, `preview_id`; returns 200 if the file already exists in storage, else 202 with a `task_id` tracked at `GET /api/tasks/{task_id}` — [openapi-cloud.yaml](https://docs.comfy.org/openapi-cloud.yaml)
- `GET /api/assets/remote-metadata?url=` previews size, filename, tags and a validation result for a remote URL such as `https://civitai.com/api/download/models/123456` before downloading — [openapi-cloud.yaml](https://docs.comfy.org/openapi-cloud.yaml)
- `HEAD /api/assets/hash/{blake3:...}` checks whether content exists in Cloud storage; `POST /api/assets/from-hash` (sha256 or blake3) creates an asset reference over existing bytes without re-upload — [openapi-cloud.yaml](https://docs.comfy.org/openapi-cloud.yaml)
- `GET /api/experiment/models` and `GET /api/experiment/models/{folder}` are public (no key) and return `{name, pathIndex}` only — no hash, size or source — [openapi-cloud.yaml](https://docs.comfy.org/openapi-cloud.yaml)
- The Cloud API reference page itself documents no model, asset or import endpoints; its only model-related item is the error type `ModelDownloadError` ("Required model not available or failed to download"); the v1 Cloud API is deprecated in favour of Comfy API v2 — [Cloud API reference](https://docs.comfy.org/development/cloud/api-reference), [Cloud API overview](https://docs.comfy.org/development/cloud/overview)

**Comfy API v2 and the Comfy SDK**
- Comfy API v2 is served by Comfy Cloud, Comfy API deployments (`https://{deployment}.run.comfy.app`) and self-hosted ComfyUI via comfy-api-proxy; its resources are Assets and Jobs only — [Comfy API v2 overview](https://docs.comfy.org/api-reference/v2/overview)
- `POST /api/v2/assets` takes `file`, `content_type` and `file_path` — "Placement path / filename (global-namespace-root form, e.g. `photo.png` or `models/checkpoints/x.safetensors`)" — plus optional `expected_hash` (blake3) — [openapi-v2.yaml](https://docs.comfy.org/openapi-v2.yaml); same field in the installed SDK types — [@comfyorg/sdk 0.5.0 types.gen.d.ts](D:/Code/comfyfield/.claude/worktrees/skills/node_modules/@comfyorg/sdk/dist/low/generated/types.gen.d.ts)
- A workflow can carry a typed asset reference where a filename would go: `{"__type": "core/ASSET", "info": {"id": "<asset-uuid>", "hash": "blake3:...", "file_path": "photo.png"}}`; an unresolvable or not-owned reference fails with 422 `missing_asset` — [openapi-v2.yaml](https://docs.comfy.org/openapi-v2.yaml)
- ComfyField's Cloud path uses the SDK: `client.workflows.fromFile(file)`, `wf.json = graph`, uploads only `LoadImage`/`LoadVideo` inputs via `client.assets.fromBytes`, then `client.run(wf, …)`; LoRA names stay plain filenames inside the graph — [server/core.js](D:/Code/comfyfield/.claude/worktrees/skills/server/core.js) (lines 697–721)
- Comfy API deployments: a Build is "the ComfyUI environment definition: its version, models, custom nodes, and dependencies"; on deploy "its models are staged onto network storage shared by the deployment's workers", read-only; workers get a 50 GB ephemeral disk — [Serverless overview](https://docs.comfy.org/development/serverless/overview). How a model URL/hash is declared in `comfy-build.yaml` is not documented on the Build Sources page — [Build sources](https://docs.comfy.org/development/serverless/build-sources)

### Inferences
- **End-to-end on Cloud with a preinstalled LoRA (the shippable path):** (1) pick a LoRA whose exact filename is in `/api/experiment/models/loras`; (2) build the API-format graph in `public/workflows/<name>.json` with a core `LoraLoaderModelOnly` (or `LoraLoader`) whose `lora_name` is that filename; (3) add a `MODEL_FILES` entry keyed by the same filename with `cloud: true` and a Hugging Face source + sha256 so a Pod can run the same graph; (4) point the format's `workflow:` at it. `runComfy` then sends it to Cloud with no extra code.
- **User-imported LoRAs do not fit the current model.** `cloud` is a static per-file flag, but an import exists only in one user's Cloud account and only on Creator+. A format that depends on an imported LoRA would need a per-user runtime check (and the user's own import), so it should not be a shipped format; a "bring your own LoRA" feature would be a separate, opt-in flow.
- `POST /api/assets/download` looks like the API form of the Import button, so ComfyField could in principle trigger imports with the user's key. It is unverified whether it is gated to Creator+ on the API, which `tags` make a file appear under `loras`, and whether the imported file is then addressable by plain filename in `/api/prompt` or v2 jobs.
- Because the Cloud listing gives no hash, a `cloud: true` entry only proves the *filename* matches. A Pod entry pinned by sha256 may hold different bytes from Cloud's copy (for example AnyLight: HF file `QIE-2511-AnyLight_.safetensors` vs Cloud `Qwen-Image-Edit-2511-AnyLight.safetensors`). Results could differ slightly between backends.
- The 100 MiB `max_upload_size` and the "local uploads are not supported" FAQ mean pushing a LoRA's bytes to Cloud through `/api/upload` or v2 assets is not a practical path; most Qwen/Wan LoRAs are 0.28–1.4 GB.
- A Comfy API deployment (Build with LoRAs staged on network storage) could bundle any LoRA, but each user would need their own deployment under their own key and credits, which fits poorly with "bring your own keys" and the contest timeline.

### Gaps
- No official statement found on whether user-imported LoRAs can be referenced by filename from the Cloud API or Comfy API v2 jobs; not testable without a Creator key (and the repo rules forbid keyed tests without a `needs-keys` issue).

## RunPod Pods: how to fetch LoRAs at boot or first run, how `shared/modelFiles.js` handles it, and exactly what a new entry needs

### Takeaway
The Pod path already downloads LoRAs like any model file: the graph names the file, `modelFilesOf()` maps the loader input to a `MODEL_FILES` entry, and the Pod's status server fetches it from `huggingface.co/<repo>/resolve/main/<path>` with resume and a pinned sha256. A new Hugging Face LoRA needs only one `MODEL_FILES` entry; a Civitai LoRA or a gated HF LoRA needs new code, because the Pod downloader accepts Hugging Face `owner/repo` sources only and sends no token.

### Cited Findings

**How the current pattern works**
- "Model files a Pod can download, by the filename a workflow's loader node names. A workflow lists nothing itself: its graph is the source of truth… Public Hugging Face repos only… The Pod checks each download against its sha256, so a mirror can only deliver the original bytes." — [shared/modelFiles.js](D:/Code/comfyfield/.claude/worktrees/skills/shared/modelFiles.js)
- `LOADERS` maps loader inputs to folders, including `LoraLoader: { lora_name: 'loras' }`, `LoraLoaderModelOnly: { lora_name: 'loras' }`, `FreeVideoLoRA: { lora: 'loras' }`. `modelFilesOf(graph)` skips `{{placeholders}}` and `'None'`, throws 400 "`<name>` is not in ComfyField's model list, so a Pod cannot download it." for unknown names, and throws if the entry's `dir` differs from the loader's folder — [shared/modelFiles.js](D:/Code/comfyfield/.claude/worktrees/skills/shared/modelFiles.js)
- `minVramOf` takes the max `vramGb`; `volumeFor` sums `gb` + 30 GB headroom — [shared/modelFiles.js](D:/Code/comfyfield/.claude/worktrees/skills/shared/modelFiles.js)
- Models download *after* the Pod is ready ("Models download after ready, so the boot deadline covers only ComfyUI and the proxy coming up"); the boot script creates `/workspace/models/{checkpoints,diffusion_models,text_encoders,vae,loras,upscale_models,latent_upscale_models,clip_vision}` and points ComfyUI at them with `extra_model_paths.yaml` — [server/podBoot.js](D:/Code/comfyfield/.claude/worktrees/skills/server/podBoot.js)
- On a Pod run, `runComfy` calls `lease({ files: needs.filter((n) => !n.runtime), … })`, which posts the file list to the Pod — [server/core.js](D:/Code/comfyfield/.claude/worktrees/skills/server/core.js) (line 704); the check suite posts `{ repo, path, dir: 'loras', name, sha256 }` to `/download` — [scripts/pod-checks.mjs](D:/Code/comfyfield/.claude/worktrees/skills/scripts/pod-checks.mjs) (line 165)
- Pod downloader (`server/pod-statusd.py`): `valid()` requires `repo` to match `^[\w.-]+/[\w.-]+$`, `dir` in the folder list, `name` to match `^[\w.+-]+$`, a relative `path` without `..`, and `sha256` (if given) to match lowercase `^[0-9a-f]{64}$`; `fetch()` builds `https://huggingface.co/<repo>/resolve/main/<path>`, resumes `.part` files with a `Range` header, hashes while streaming, deletes the part and fails on a sha256 mismatch, and saves to `/workspace/models/<dir>/<name>`; 3 attempts, but 401/403/404, disk full and hash mismatch fail at once; files already on the volume are marked done — [server/pod-statusd.py](D:/Code/comfyfield/.claude/worktrees/skills/server/pod-statusd.py)
- ComfyUI on the Pod starts with `--disable-all-custom-nodes --whitelist-custom-nodes FreeVideo`, so only core nodes and FreeVideo load — [server/podBoot.js](D:/Code/comfyfield/.claude/worktrees/skills/server/podBoot.js)
- Existing LoRA entries: LightX2V T2V turbo (`Kijai/WanVideo_comfy`, 0.63 GB, `cloud: true`), BFS head swap high/low (`Alissonerdx/BFS-Best-Face-Swap-Video`, 0.61 GB each, `cloud: false`, `label`), MiniMax H3 FL2V turbo 8-step (`Comfy-Org/MiniMax-H3`, 1.96 GB, `cloud: true`) — [shared/modelFiles.js](D:/Code/comfyfield/.claude/worktrees/skills/shared/modelFiles.js)
- Gated HF repos are avoided by using ungated mirrors whose sha256 matches the official file ("the official Lightricks/LTX-2.5 is gated, so these come from ungated mirrors whose sha256 matches the official files exactly") — [shared/modelFiles.js](D:/Code/comfyfield/.claude/worktrees/skills/shared/modelFiles.js)

### Inferences
- **Exact recipe for a new Hugging Face LoRA (no code change):**
  1. Read `https://huggingface.co/api/models/<repo>?blobs=true` for `gated` (must be `false`), `cardData.license`, the file's `rfilename`, `size` and `lfs.sha256`.
  2. Add one `MODEL_FILES` entry keyed by the exact filename the graph's `lora_name` will use. If Cloud already lists the LoRA, use Cloud's filename as the key (even when HF's differs) so one graph runs on both backends. Example for Multiple-Angles:
     `'qwen-image-edit-2511-multiple-angles-lora.safetensors': { repo: 'fal/Qwen-Image-Edit-2511-Multiple-Angles-LoRA', path: 'qwen-image-edit-2511-multiple-angles-lora.safetensors', dir: 'loras', gb: 0.30, vramGb: 0, cloud: true, sha256: '42426ded4e25fd22879d9e198b857556445ef4ca56e8da3246d0345155bb6765' }`
  3. Fields: `repo` (owner/name), `path` (path inside the repo), `dir: 'loras'`, `gb` (decimal GB, used for disk sizing), `vramGb: 0` (LoRAs do not raise the GPU tier), `cloud` (true only if the filename is in Cloud's `loras` listing), `sha256` (lowercase), and `label` when `cloud: false` (it becomes the user-facing "… is not on Comfy Cloud yet" text).
  4. Use a core `LoraLoader`/`LoraLoaderModelOnly` in the graph (or extend `LOADERS` for a new loader node; a loader missing from `LOADERS` makes the file invisible, so the Pod would not download it and the Cloud check would pass wrongly).
  5. Run `node scripts/pod-checks.mjs` (it already tests LoRA downloads and Cloud/Pod routing) plus the CI trio.
- **Civitai or gated-HF LoRAs need code:** (a) a second source shape in `MODEL_FILES` and `valid()`/`fetch()` (for example `{ civitai: <versionId>, fileId }` → `https://civitai.com/api/download/models/<versionId>?fileId=<fileId>`), (b) lowercase Civitai's uppercase SHA256, (c) an optional token passed per download request rather than baked into the boot env. Python's `urllib` keeps ordinary request headers on redirects, so a Bearer header would be forwarded to `b2.civitai.com`; `add_unredirected_header` avoids that. The downloader already fails fast on 401/403, which would surface "needs a token".
- A simpler interim route for a Civitai-only LoRA with permissive terms: mirror it to a ComfyField-controlled public HF repo (if its permissions allow redistribution) and pin the original sha256, as the repo already does for gated mirrors.
- The proxy upload route is a poor fit: the 100 MB default cap is below most LoRA sizes, and files would land under `$H3/ComfyUI/models` on the container disk rather than the `/workspace/models` volume.
- LoRA files are small next to base models (0.05–2 GB vs 15–22 GB), so the extra Pod cost is a few seconds to a minute of download on the first run and a little volume space; ComfyField bills paused volumes at `STOPPED_DISK_USD_GB_MONTH = 0.2` per GB-month — [server/pod.js](D:/Code/comfyfield/.claude/worktrees/skills/server/pod.js).

### Gaps
- No RunPod doc found on setting `RUNPOD_SECRET_*` references when creating a Pod via the API (ComfyField creates Pods via API, not templates).
- Civitai rate limits for `/api/download` were not found in the docs read.
- Whether Civitai's `requireAuth` downloads accept a token from a server on behalf of another user (vs. the user's own token) under Civitai's terms was not checked.

## Civitai permission flags and Hugging Face license fields: what they mean for a hosted or open-source tool, and how to record them

### Takeaway
Civitai stores per-model permissions as `allowNoCredit`, `allowDerivatives`, `allowDifferentLicense` and an `allowCommercialUse` array of `Image`, `RentCivit`, `Rent`, `Sell`, `SellMerge`; for a service that runs models for users, the key flag is `Rent` ("Use on other generation services"). Hugging Face exposes the license as `cardData.license` (plus `license_name`/`license_link` for `other`) and gating as `gated`. Both are cheap to record per `MODEL_FILES` entry for the after-submission license review.

### Cited Findings
- Civitai uploader labels (source code): `Image` = "Sell generated images", `RentCivit` = "Use on Civitai generation service", `Rent` = "Use on other generation services", `Sell` = "Sell this model", `SellMerge` = "Sell merges using this model"; checkboxes `allowNoCredit` = "Use without crediting me", `allowDerivatives` = "Share merges of this model", `allowDifferentLicense` (shown only when merges are allowed); all three default to `true` on a new model — [ModelUpsertForm.tsx](https://github.com/civitai/civitai/blob/main/src/components/Resource/Forms/ModelUpsertForm.tsx)
- Civitai's public permission panel wording: "Run on services that generate for money" (`Rent`), "Run on Civitai" (`RentCivit`), "Sell images they generate", "Use the model without crediting the creator", "Share merges using this model", "Sell this model", "Sell merges using this model", "Have different permissions when sharing merges"; summary badges "Generation services allowed" if `RentCivit` or `Rent`, "Creator credit required" if not `allowNoCredit` — [PermissionIndicator.tsx](https://github.com/civitai/civitai/blob/main/src/components/PermissionIndicator/PermissionIndicator.tsx)
- Civitai: "these are guidelines, using the honor system", and Civitai "will not pursue legal claims on your behalf"; options include "Commercial Use – None"; "Use on other generation services" lets "Off-site generation services… use the model for their own image generation services"; a model trained on a real person must be flagged, cannot be used on Civitai's Generator, and adult content of a real person violates the ToS — [Civitai education: Uploading content](https://education.civitai.com/using-civitai-uploading-content/)
- API shape: `allowCommercialUse` is returned as an array, e.g. `["Image","RentCivit","Rent","Sell","SellMerge"]`, `["RentCivit"]` or `[]`; also `allowNoCredit`, `allowDerivatives`, `allowDifferentLicense`, `availability`, `mode` — [Civitai models reference](https://developer.civitai.com/site/reference/models.md); live sample of the 20 most-downloaded Qwen LoRAs — [civitai.com/api/v1/models?types=LORA&baseModels=Qwen](https://civitai.com/api/v1/models?types=LORA&limit=20&sort=Most%20Downloaded&baseModels=Qwen&nsfw=false)
- Live sample spread: 9 of 20 allow everything (`Image, RentCivit, Rent, Sell, SellMerge`); "Qwen Edit Reality Transform By Aldniki", "Qwen Edit Figure Maker By Aldniki" and "Reality Simulator" allow only `RentCivit`; "Consistence Edit Lora" and "[Flux2Klein 9B] Anything2Real" return `[]`; "Lenovo UltraReal" allows `Rent` but requires credit (`allowNoCredit: false`) — [Civitai models API sample](https://civitai.com/api/v1/models?types=LORA&limit=20&sort=Most%20Downloaded&baseModels=Qwen&nsfw=false)
- Comfy Cloud preinstalls `Qwen-Image-Edit-reality_transform_by_aldniki.safetensors` and `qwen-lenovo_ultrareal.safetensors`, whose names match two of those Civitai models — [Cloud loras listing](https://cloud.comfy.org/api/experiment/models/loras)
- Hugging Face: the license is set in the model card's YAML `license:` field using identifiers such as `apache-2.0`, `mit`, `openrail`, `creativeml-openrail-m`, `openrail++`, `cc-by-nc-4.0`, `other`; with `license: other`, the repo adds a `LICENSE` file and a `license_name` — [HF docs: Licenses](https://huggingface.co/docs/hub/repositories-licenses). The API returns it as `cardData.license` and as `license:` tags (e.g. `license:apache-2.0`) — [HF API: fal Multiple-Angles](https://huggingface.co/api/models/fal/Qwen-Image-Edit-2511-Multiple-Angles-LoRA?blobs=true)
- Hugging Face gated repos: automatic or manual approval; users must be logged in and accept; scripts must send a user token; "The model authors have complete control over model access… they can decide at any time to block your access"; authors can also block EU users with `extra_gated_eu_disallowed` — [HF docs: Gated models](https://huggingface.co/docs/hub/models-gated)
- Many LoRA licenses inherit from the base model; ComfyField's notes record the BFS head-swap repo as tagged "other" with an LTX-2 community license — [research_notes/engine/genjutsu.md](D:/Code/comfyfield/.claude/worktrees/skills/research_notes/engine/genjutsu.md); the FLUX 3 Klein weights note "The FLUX Kommunity License still applies to the weights" — [shared/modelFiles.js](D:/Code/comfyfield/.claude/worktrees/skills/shared/modelFiles.js)

### Inferences
- **What the flags mean for ComfyField** (after-submission checklist, not a blocker):
  - ComfyField is open-source code; users run models on their own Cloud account or their own Pod with their own keys. That is closest to "the user runs the model" rather than "ComfyField is a generation service", but any hosted ComfyField instance that charges users would be an off-site generation service, which needs `Rent`.
  - `RentCivit` alone does not cover ComfyField; `[]` means no commercial use at all.
  - `allowNoCredit: false` means the format's info/credits should name the creator and link the model page.
  - `Image` matters to end users (selling outputs), so it is worth showing in the UI.
  - `Sell`/`SellMerge`/`allowDerivatives` matter only if ComfyField redistributes or merges weights (e.g. an HF mirror of a Civitai LoRA, which redistributes the file and is not covered by any of these flags directly).
  - A LoRA's own permissive tag does not override the base model's license (FLUX dev-style non-commercial terms, LTX-2 community license, MiniMax H3 community license).
- Comfy hosting a LoRA on Cloud does not by itself grant ComfyField rights; the Aldniki example shows Cloud preinstalls at least one file whose Civitai page withholds `Rent`, so preinstalled files still need a source check.
- **How to record:** add optional fields to each `MODEL_FILES` LoRA entry, for example `source: 'hf' | 'civitai'`, `page` (model URL), `license` (HF `cardData.license` or Civitai base license), `gated`, `civitai: { versionId, allowCommercialUse: [...], allowNoCredit, allowDerivatives, allowDifferentLicense }`, `credit` (creator name), and `checked: '2026-10-19'`. For a Cloud-only file, look up its Civitai page by hash where the bytes are known (`/model-versions/by-hash/{sha256}`).

### Gaps
- No official Civitai statement found on whether an open-source app that only orchestrates the user's own GPU or Cloud account counts as an "other generation service".
- Civitai's general Terms of Service on automated downloads and redistribution of LoRA files were not read.
- The provenance (HF vs Civitai, which version) of Cloud's preinstalled third-party LoRAs is not published; filename matches are not proof.

## ComfyUI support: do current core LoRA loaders handle each target model, which need custom nodes, and are those nodes on Comfy Cloud?

### Takeaway
ComfyUI v0.41.1 (the version on both Cloud and ComfyField's Pod) loads LoRAs natively with core `LoraLoader`/`LoraLoaderModelOnly` for every target: Qwen-Image (incl. 2.1 and Edit), FLUX 3, Z-Image, HiDream-O1, Wan 2.2, LTX-2/2.3/2.5 and MiniMax H3, and LTX IC-LoRAs have core helper nodes. ## How many LoRAs can be stacked per run, and how do speed / distill LoRAs interact with style LoRAs?

### Takeaway
ComfyUI has no hard cap: LoRA loaders chain, each with its own strength. Practical limits come from quality, not software: test each LoRA alone, then chain, and only combine a speed LoRA (Lightning, LightX2V, distilled, turbo) with a style LoRA when the cards or a test show they work together.

### Cited Findings
- Multiple LoRAs are applied by chaining `Load LoRA` nodes; "Adjust `strength_model` values in both `Load LoRA` nodes to control each LoRA's influence"; no maximum is stated — [Comfy docs: Multiple LoRAs](https://docs.comfy.org/tutorials/basic/multiple-loras)
- Strength inputs range −100 to 100 per loader; the loader returns early when both strengths are 0 — [ComfyUI nodes.py @45bf90d](https://github.com/comfyanonymous/ComfyUI/blob/45bf90d1c91eecd782643346dcfb73cb0017667f/nodes.py)
- Lightricks: "The LoRA's model card takes precedence over any generic value"; if none, "test at `1.0` first, then change only the strength"; "Avoid universal strength caps. The useful range depends on the LoRAs, their training, the base model, and the workflow"; verify each LoRA alone, then chain and "connect the final modified MODEL output to every sampler stage"; combine effect and IC-LoRAs only "when the LoRA cards and workflow establish compatibility" — [LTX docs: LoRAs](https://docs.ltx.io/open-source-model/usage-guides/lo-ra). Conflict: a search snippet of an older version of this page said to keep total combined strength under 2.0; the current page does not say this.
- Qwen-Image-Lightning: distilled LoRA for fewer steps; the example uses 8 steps with `true_cfg_scale=1.0`; "We use shift=3 in distillation"; Apache-2.0; the card says nothing about combining with other LoRAs — [lightx2v/Qwen-Image-Lightning](https://huggingface.co/lightx2v/Qwen-Image-Lightning)
- Wan2.2-Lightning: "Video generation now requires only 4 steps without the need of CFG trick"; artifacts possible with "extremely large motion"; Apache-2.0; the card says nothing about combining with other LoRAs — [lightx2v/Wan2.2-Lightning](https://huggingface.co/lightx2v/Wan2.2-Lightning)
- ComfyField precedent: the Bernini-R swap runs LightX2V turbo at 6 steps; "Quality mode (template 'Turbo OFF'): remove both LightX2V LoRAs, 40 steps, split 20, CFG 5"; the head-swap graph drops LightX2V and runs the BFS LoRAs at 1.0 with 40 steps — [research_notes/engine/genjutsu.md](D:/Code/comfyfield/.claude/worktrees/skills/research_notes/engine/genjutsu.md)
- Cloud ships speed LoRAs next to style LoRAs for the same base (e.g. `Qwen-Image-Edit-2511-Lightning-4steps-V1.0-bf16` alongside 2511 relight/angle LoRAs; `z_image_turbo_distill_patch_lora_bf16` alongside `zimage-*` styles; `ltx-2.3-22b-distilled-lora-384` alongside LTX-2.3 IC-LoRAs) — [Cloud loras listing](https://cloud.comfy.org/api/experiment/models/loras)

### Inferences
- Speed LoRAs change the sampler recipe (steps, CFG ≈ 1, shift), so a format that stacks one must set those, and a style LoRA's card strength (usually tuned at full steps and normal CFG) may need lowering. Treat "style + speed" as a recipe to test per pair, with a "quality" variant that drops the speed LoRA, as the Bernini-R graphs already do.
- For Wan 2.2, a stack is per expert: N LoRAs means up to 2N loaders (high and low), with different strengths per expert.
- For the contest, keep stacks at one task LoRA (relight, angles, head swap) plus at most one speed LoRA. Each extra LoRA is another file to pin, another license to record, and another failure mode.
- Each chained LoRA patches model weights at load, so stacks add load time and memory; with ComfyUI's caching, a repeat run with the same stack should be cheaper (not measured).

### Gaps
- No primary source found with measured quality results for Qwen-Image-Lightning or Wan2.2-Lightning stacked with style LoRAs.
- No primary source found on the speed cost of each extra LoRA on Cloud or on a Pod.
